## [T0.1] Docker Compose 基础设施 —— 2026-08-29

**状态**：已完成

**完成内容**：
- 仓库根目录新增 `docker-compose.yml`：`postgres`（16）、`redis`（7，`--requirepass` + `--appendonly yes`）、`minio`（`minio/minio:latest`）三个服务，均用具名 volume（`postgres_data`/`redis_data`/`minio_data`）持久化，统一挂在 `agent-builder-net` bridge 网络下，各自带 healthcheck
- 新增一次性 `minio-init` 服务（`minio/mc:latest`），依赖 `minio` healthy 后自动创建两个 bucket，`mc mb --ignore-existing` 保证幂等、可重复 `up`
- 新增 `.env.example`（字段：Postgres/Redis/MinIO 的地址、账号密码、库名、bucket 名、端口），`.gitignore` 忽略 `.env`

**关键决策与偏差**：
- Bucket 方案选了"两个独立 bucket"而非前缀区分：`agent-builder-skills`（Skill zip）、`agent-builder-workspaces`（Workspace 快照，仓库快照/输出快照用 object key 前缀在同一 bucket 内区分）。已回写到 [TASKS.md](../TASKS.md) T0.1
- 本机开发环境 5432/6379/9000 三个默认端口均被其他项目占用，`.env.example` 里把宿主机侧映射改成了 5442（Postgres）/6389（Redis）/9010+9011（MinIO API+控制台），容器内部仍是标准端口，纯粹是本机开发环境的规避，不是架构决策，不影响 compose 网络内以服务名（`postgres`/`redis`/`minio`）访问
- compose 文件用了顶层 `name: agent-builder` 而非目录名推断项目名，避免不同签出路径下项目名不一致导致 volume/network 名漂移

**验收验证过程**（对应 TASKS.md 验收标准）：
- `docker compose up -d` 一键拉起三个服务，`docker compose ps` 确认三者都是 `healthy`
- 用 `psql`（docker exec）建表插入查询、`redis-cli -a`（docker exec）set/get、一次性 `minio/mc` 容器 cp/cat/rm 分别验证了三个组件的读写
- `docker compose restart postgres redis minio` 后验证 Redis 中之前写入的 key 仍在（volume 持久化生效），且 healthcheck 恢复 healthy

**遗留问题**：
- 无。这是纯基础设施任务，业务代码骨架从 T0.2 开始

**给下一个任务的建议**：
- T0.2（Backend API 骨架）读取 `.env` 时直接复用这里的字段名（`POSTGRES_*`/`REDIS_*`/`MINIO_*`），不要重新定义一套命名
- Compose 网络内部访问三个组件请用服务名 `postgres`/`redis`/`minio` + 标准端口（5432/6379/9000），不要用 `.env` 里为宿主机规避冲突而改的端口号（那些只用于宿主机 -> 容器的端口映射）
- 两个 bucket 名固定为 `agent-builder-skills` / `agent-builder-workspaces`，T1.2（Skill Service）和 T2.3（Workspace 初始化）直接读 `.env` 里的 `MINIO_BUCKET_SKILLS` / `MINIO_BUCKET_WORKSPACES`，workspace 快照记得自己约定仓库快照 vs 输出快照的 object key 前缀（本任务未定义，留给 T2.3 或更早的 T1.1 数据模型任务时一并定）
- 本地验证 MinIO 读写时如果要再跑一次性 `mc` 命令，注意 `minio/mc` 镜像的 entrypoint 已经是 `mc` 本身，需要 `--entrypoint sh` 才能跑多条命令的 shell 脚本（当时踩了一次坑）

## [T0.2] Backend API 项目骨架 —— 2026-08-29

**状态**：已完成

**完成内容**：
- 新增 `backend-api/` FastAPI 项目骨架：

  - `app/logging_config.py` —— `structlog` 配置，JSON 结构化日志输出到 stdout

  - `app/main.py` —— FastAPI app 工厂，`lifespan` 里建立/释放连接池
  - `app/api/health.py` —— `GET /health`，数据库不通时返回 HTTP 503 + `status: degraded`
  - `app/modules/{skills,mcp,agents,conversations,auth}/` —— 预留的业务模块空目录（仅占位注释，指向对应后续任务 ID）
  - `requirements.txt` / `requirements-dev.txt`（含 pytest/httpx）/ `Dockerfile` / `.dockerignore` / `pytest.ini`
  - `tests/test_health.py` —— 用 `httpx.ASGITransport` 直接测 FastAPI app，不需要真实起服务
- `docker-compose.yml` 新增 `backend-api` service：`build: ./backend-api`，`env_file: .env` 但覆盖 `POSTGRES_HOST/PORT`、`REDIS_HOST/PORT`、`MINIO_HOST/PORT` 为 compose 服务名 + 标准端口；`depends_on` 三个依赖服务的 `service_healthy`；自带 healthcheck（用 `python -c` 探活 `/health`，避免镜像里没有 curl）
- `.env.example` 补充 `BACKEND_API_PORT=8080`、`LOG_LEVEL=INFO`；并把 `POSTGRES_HOST`/`REDIS_HOST`/`MINIO_HOST` 的默认值从 compose 服务名改成 `localhost`（配合上面 compose service 里的覆盖机制，见 TASKS.md T0.2 决策记录）

**关键决策与偏差**：
- 详见已回写到 [TASKS.md](../TASKS.md) T0.2 的"决策记录"小节：技术选型（pydantic-settings + SQLAlchemy async/asyncpg + structlog）、`.env` 里 HOST/PORT 的"宿主机本地开发默认值 vs compose service 覆盖值"两套语义、`/health` 用 503 区分依赖不可用与进程存活
- `get_settings()` 用了 `lru_cache`，意味着"改 `.env` 生效"是通过**重启进程**，不是运行时热更新——验收标准里"修改 `.env` 能连到不同数据库实例"按重启后生效验证通过，不要误解成支持热加载

**遗留问题**：
- 无阻塞项。当前 `/health` 只探测 Postgres；Redis/MinIO 连通性检查留给 T0.3（Runner 骨架的健康检查同时覆盖 Redis/MinIO/Postgres）和后续对应模块任务时再补，本任务按 TASKS.md T0.2 验收标准（只要求数据库连通性）执行
- `backend-api/.venv` 是本次验证时本地建的虚拟环境，已在根 `.gitignore` 的 `.venv/` 规则里排除，不会被提交

**给下一个任务的建议**：
- T1.x 系列（Skill/MCP/Agent Service）直接在 `app/modules/<name>/` 下扩展 router + service + schema，再在 `app/main.py` 里 `include_router`，不要新建平行的目录结构
- 数据库 session 目前只有 `get_session_factory()`，T1.1（数据模型与迁移）落地时需要补一个 FastAPI 依赖项（如 `app/api/deps.py` 里的 `get_db_session`）供各业务 router 用，本任务未创建是因为还没有 ORM 模型可用
- 本地开发起服务：`cd backend-api && cp ../.env .`（或自行维护一份 `backend-api/.env`）然后 `uvicorn app.main:app --reload`；容器方式：根目录 `docker compose up -d --build backend-api`
- Windows/Git Bash 下 `pkill` 对 `python.exe` 子进程经常杀不掉，要按端口找 PID 用 PowerShell 的 `Get-NetTCPConnection -LocalPort <port> | Stop-Process`，这次验证时踩了这个坑
